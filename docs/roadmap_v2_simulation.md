# Project MANA 次バージョン計画: 厳密な対戦シミュレーションと完全な強さ判定

本書は、READMEで「まだ含めていません」と明記している以下2項目を実現するための設計・ロードマップです。

- 厳密な対戦シミュレーション
- 完全な強さ判定

対象バージョンは v1.1(基盤整備)→ v1.2(ルールエンジンMVP)→ v2.0(モンテカルロ対戦による強さ判定)の3段階を想定します。

## 1. 現状整理(v1.0.0)

- マナ支払い、シールド、ブロッカー、召喚酔い、S・トリガーなどの実ルール処理

- 合法手の列挙と選択(ゲーム木が存在しない)

`src/battle/` ディレクトリは `__init__.py` のみの空パッケージであり、ルールエンジンの置き場所として予約済みです。

## 2. 目標アーキテクチャ

```
┌─────────────────────────────────────────────┐
│ 強さ判定レイヤー (v2.0)                        │
│  モンテカルロ自己対戦 / メタ対戦 / 勝率CI集計     │
├─────────────────────────────────────────────┤
│ 対戦シミュレーションレイヤー (v1.2)              │
│  ゲーム状態 / ターン進行 / 合法手生成 / 方策AI    │
├─────────────────────────────────────────────┤
│ 効果DSLレイヤー (v1.1〜v1.2)                   │
│  能力テキスト → 構造化効果 (EffectScript)       │
├─────────────────────────────────────────────┤
│ ルールカーネル (v1.1)                          │
│  ゾーン / マナ支払い / シールド / 攻撃・ブロック   │
└─────────────────────────────────────────────┘
```

すべて `src/battle/` 配下に新設し、既存のヒューリスティック群(`battle_simulator.py` 等)は当面残して比較対象として使います。

### 2.1 ルールカーネル(`src/battle/kernel/`)

最小限のルールを正確に実装します。

- `GameState`: 両プレイヤーの 山札 / 手札 / マナゾーン / バトルゾーン / シールドゾーン / 墓地 を保持する不変データ構造
- ターン構造: 開始 → ドロー → チャージ(任意1枚)→ メイン(召喚・呪文)→ 攻撃 → 終了
- マナ支払い: 文明拘束を含むコスト支払い判定(タップ管理)
- 攻撃処理: 召喚酔い、プレイヤー攻撃/クリーチャー攻撃、ブロッカー宣言、パワー比較
- シールド処理: ブレイク → 手札追加 → S・トリガー即時使用ウィンドウ
- 勝敗判定: シールド0でのダイレクトアタック、山札切れ、特殊勝利フック

### 2.2 効果DSL(`src/battle/effects/`)

能力テキストを直接実行するのではなく、**構造化された効果記述(EffectScript)** を中間表現として導入します。

```json
{
  "card_id": "DMPC-0001",
  "abilities": [
    {"trigger": "on_cast", "actions": [{"op": "deck_top_to_mana", "count": 1}]}
  ]
}
```

- 第1段階: `effect_semantics.py` のキーワード抽出結果からEffectScriptの**下書きを自動生成**し、人手でレビュー・修正するワークフロー(既存のCSV管理画面の延長)
- 第2段階: レビュー済みEffectScriptを `card_effects` テーブル(新設)に保存し、カーネルが解釈実行
- 対応する命令セットは段階的に拡張(ドロー、マナ加速、破壊、バウンス、S・トリガー、ブロッカー、踏み倒しの順を想定)

全カードの完全対応は目指さず、**EffectScript未定義カードは「バニラ扱い+警告」**で動かせる設計にします(段階導入の要)。

### 2.3 シミュレーションエンジン(`src/battle/sim/`)

- 合法手列挙: 現在の `GameState` から打てる手(チャージ選択、召喚、呪文、攻撃対象、ブロック宣言)をすべて列挙
- 方策AI(段階導入):
  1. ランダム方策(動作検証用)
  2. 貪欲方策(`state_transition_model.py` のpayoff/speed/stabilityスコアを評価関数に流用)
  3. 1〜2手読みの先読み方策
- 1試合を再現可能にする乱数シード管理と、ターンごとの行動ログ出力(研究ログとしてSQLite保存)

### 2.4 強さ判定(`src/battle/rating/`)

- モンテカルロ対戦: デッキペアごとにN試合(既定200〜1000)実行し、勝率と95%信頼区間を算出
- メタ対戦評価: `meta_decks` テーブルの実メタレシピと総当たりし、加重平均勝率を「絶対強さスコア」として算出
- 既存スコアとの突き合わせ: `evaluate_deck.py` のヒューリスティックスコア、実戦ログ(`real_match_logs`)の実勝率と三つ巴で比較し、各指標の予測力を検証
- コンボ検証: `state_transition_model.py` が提案するチェーンをカーネル上で再生し、「実際に成立するか」を判定

## 4. データモデル変更

- 新設 `card_effects`(card_id, effect_json, review_status, updated_at): EffectScript本体
- 新設 `sim_battle_logs`(session_id, deck_a, deck_b, seed, winner, turns, action_log_json): 厳密シミュレーション結果

## 5. リスクと方針

- **効果テキストの網羅は不可能**: EffectScript未定義カードを許容する段階導入とし、カバレッジ(定義済みカード率)をダッシュボードに表示する
- **ルールの完全再現は目指さない**: 超次元・革命チェンジ等の複雑メカニズムはv2.0以降に先送りし、未対応メカニズム使用時は明示的に警告する
- **方策AIの弱さが勝率を歪める**: 同一方策同士の対戦に限定して相対比較する。方策強化は独立した改善ループとする
- **既存ヒューリスティックは廃止しない**: 計算コストが軽く候補探索(進化探索)には引き続き有効なため、「探索はヒューリスティック、検証は厳密シミュレーション」の二段構えとする
